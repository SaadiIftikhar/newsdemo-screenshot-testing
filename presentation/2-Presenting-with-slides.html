Presenting with slides

The full talk, slide by slide: what to say, what to open or run, and what to do if a live step fails. The same text is in the PowerPoint speaker notes. About 22 minutes, then questions.

How to present it

  • Rhythm for every LIVE slide: tell (what to look for) → show (one command, point at one thing) → tell again (what it proved), then back to the slides with Cmd+Tab.
  • Screens: with two screens, use Presenter View. With one laptop on a call, share the whole screen and keep this page on a second device or printed.
  • Copying commands: press Copy, Cmd+Tab to Terminal, Cmd+V, Enter. Read the command out loud as you run it.
  • Short on time: skip the steps marked "(Optional)" and slide 8's code. Never skip slide 6.

Slide 2 · The problem: too many states to check by hand

about 1.5 min

Goal: Make them feel the problem; plant the PLUS-badge example you'll use in the demo.

Say

Four apps share one design system, on two platforms. A single news feed has dozens of visual states, and all of them depend on data from the backend: breaking news, live tickers, PLUS articles, ads, offline, dark mode, accessibility text sizes, very long German words.

Checking these by hand before every release doesn't scale. And the bugs that cost money are small. My example for today: a refactor that silently drops the PLUS badge. The screen still looks fine, so nobody notices. But paid articles now look free.

Slide 3 · The approach in one picture

Goal: They understand fixture → render → golden, and see that each is a real file.

Say

Three steps. One: JSON fixtures, frozen fake API data. Two: the test renders the real production screen with that data, in memory. Three: it compares the picture with a "golden", an approved screenshot stored in git. Same picture: pass. Different: fail, with a diff image.

Because every input is frozen, a difference can only mean the code changed how the screen looks. Let me show you the three pieces.

Slide 7 · Review: machines compare, people decide

about 1.5 minLIVE · Browser

Goal: Show the decision path, and that it ran for real on GitHub.

Say

When a pull request fails, the bot posts one comment that lists the changed screens and what kind of change each is. A human opens the diff gallery and decides.

Not intended, like the badge: fix the code, the goldens stay. That's this pull request: blocked. Intended, like a redesign: add the record-snapshots label. CI re-records the goldens on its fixed machine, proves them, and pushes them as a bot commit; a design or QA code owner approves the image diff. That's this second pull request. Goldens never come from a laptop, and approval is never automatic.

Slide 8 · How much difference is allowed?

about 1.5 min

Goal: Show you thought about tolerance and human confirmation.

Say

Rendering noise is ignored: a perceptual precision of 0.98 absorbs GPU anti-aliasing. Anything beyond noise fails, however small. A 2-point shift and a missing badge are both small, and both are bugs: a pixel count can't tell intent.

So the labels are triage, not approval. Tolerance is never loosened globally; a per-test exception needs a comment and a review.

Do
  1. VS Code(Optional, if asked) the tolerance in code.
    open -a "Visual Studio Code" ios/NewsKit/Tests/NewsUISnapshotTests/SnapshotSupport.swift
    You'll see: perceptualPrecision: 0.98, and why, in the comment.
Then Cmd+Tab back to the slideshow.

Likely questions

"Who approved these goldens?"
I did, as the code owner. The AI did a first pass and caught real bugs, but approving goldens and merging pull requests were never delegated. That's the process I propose: AI may triage, a human approves.
"A test fails on CI but passes on my Mac. How do I debug it?"
CI is the source of truth and records the goldens. Download the ios-snapshot-diffs artifact from the run; the PR comment already says what kind of change it is. Then check the pinned simulator runtime: the same runtime on the Mac reproduces CI exactly.
"You replaced the native tab bar because the tool couldn't capture it. Would you change product UI for a test tool?"
No, that was a demo shortcut. In production: keep the system tab bar, snapshot the tab content, and cover system chrome in the nightly device layer.
"BILD has years of UIKit and a singleton API client. What do you ship in the first two weeks?"
Snapshots of design-system components that take plain models, a URLProtocol stub serving the fixtures as a stopgap, one client seam at one feature boundary, and CI in report-only mode.
"Show me a regression that passes your tolerance."
A colour change below about ΔE 2, like a slight brand-colour tweak. That's why colour tokens have their own contrast tests, and design reviews token changes.
"News changes every minute. How do goldens stay valid?"
They belong to frozen fixtures, not live content. The shape of real data is tested separately: contract tests, the fuzz test, hostile-content fixtures; fixtures are refreshed from real responses in their own PR.
"How fast and how expensive at scale?"
A full iOS run on GitHub is 12–19 minutes including UI tests. At scale: only affected modules, sharding, iOS only when iOS code changes, the slowest checks nightly. Target: under 10 minutes per PR.
"What about flaky tests?"
No automatic retries, because they hide flakiness. Quarantine within 24 hours with an owner. CI found one real flake, a UI test racing an animation, and I fixed the cause.
"Why only iOS? What about Android?"
I built both first; the Android version used Roborazzi on Robolectric with the same fixtures and test names, and found real cross-platform bugs. I cut it to keep the demo focused; STRATEGY §10 and the Android slide describe it.
"How did you use AI?"
As a pair programmer: research, code, docs, running the tests. I made the scope and product decisions and approved the results; PROMPTS.md lists every prompt and decision.

Can't answer one? "Good question; I haven't measured that. Here's how I'd find out: …", then name the test or experiment.
