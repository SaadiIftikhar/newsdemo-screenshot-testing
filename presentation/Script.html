Screenshot testing with mocked data: the demo

About 15 minutes plus questions. It follows two demo rules: show the result first, then how it works; and for each part tell what they'll see, show it, then tell what it means.

Before you start

Run this in Terminal 15–30 minutes before. It checks main passes and the regression fails on exactly 29 screenshots, then opens every window in the order below. About 3 minutes.

cd ~/Desktop/Task && presentation/setup.sh

The flow

1 Problem→2 Result first→3 The app→4 How it works→5 Why it doesn't go stale→ 6 Green→7 Break it→8 Who decides→9 Messy content→10 Strategy→11 Close

Why this order: the audience sees the payoff in minute 2, so everything after it answers "how?". The live failure (7) comes once they understand what a golden is (4–5), so the red result means something to them.

1

The problem

1 min
Tell

Hi, I'm Saad. The challenge: how do we catch visual bugs in the BILD and WELT apps before readers see them, when the news on screen changes every minute?

  1. TerminalJust talk; nothing to show yet.
    Say

    Some bugs don't break any logic, they break the look: a PLUS badge disappears, a headline gets cut off, a banner shrinks. Normal tests don't notice, because the code still works. Readers do. Screenshot tests catch this: they compare every screen with a picture someone approved. The catch is live news: if the data changes, every picture changes. So my answer has two parts: screenshot tests, and frozen fake data.

5

Why the pictures don't go stale

1 min
Tell

The key design decision: freeze everything that varies.

  1. VS CodeTab 3 FixtureStore.swift, FixtureEnvironment.
    Say

    A golden belongs to a fixture, not to live news. The data is frozen, and so are the clock, the German locale, the Berlin time zone, images, animations and random numbers, on one pinned simulator. "vor 9 Min." stays "vor 9 Min." forever. So when a picture changes, the only possible reason is the code. Changes in the real API's shape are caught separately, by contract tests, without pictures.

TakeawayEvery failure means something, so nobody learns to ignore red.

8

A person decides

1 min
Tell

A failing test doesn't mean "bug". It means "something changed, look at it".

  1. BrowserStay on the diff report.
    Say

    If the change is a bug, like this one, the developer fixes the code and the goldens stay. If it's intended, say a redesign, the goldens are re-recorded on one fixed machine, never on someone's laptop, and a design or QA owner approves the new pictures. A machine can tell what changed; only a person can tell whether it was meant to. Approval is never automatic.

TakeawayMachines compare; people approve.

10

The strategy: both platforms, and the rollout

2 min
Tell

The demo is iOS; the strategy covers iOS and Android.

  1. PreviewSTRATEGY.pdf, the Android section (§10).
    Say

    Android works the same way. It reads the same fixture files and uses the same test names, so one regression fails in the same places on both. The tool there is Roborazzi, which draws Compose screens on the JVM, no emulator. I built the Android version first too, and it found a real bug: a decoder difference that made a PLUS article free on Android. I cut it from the demo to keep the scope tight and the demo deep rather than wide.

  2. PreviewThe rollout section (§9).
    Say

    Rollout: start with one app and a few design-system components in report-only mode, so nothing blocks; add the shared fixtures; then make the check required on every pull request, in about four sprints. Developers write the tests with the feature, QA owns the system around them, and design approves the goldens.

TakeawayShared fixtures make it one approach across both platforms, introduced without slowing teams down.

11

Close

0.5 min
  1. TerminalStay on main.
    Say

    Three things to remember. Frozen data makes every difference meaningful. Machines compare, but a person decides. And the same fixtures carry it to Android. Everything is in the repository: the strategy, the README and the prompts I used. Happy to take questions.

If they ask

"How do you stop tests failing on tiny rendering differences?"
A perceptual precision of 0.98 ignores noise no person can see. Anything visible fails, however small: a 2-point shift and a missing badge are both bugs.
"Where does this run, and when?"
Locally with one command, and in CI on every pull request as a required check (STRATEGY §5). Goldens are recorded only there, on one pinned machine.
"How do you add a new screen?"
Write the test, run make ios-record-missing to record only the new goldens, look at them, and commit them for review.
"What if the API changes?"
Contract tests fail first, not screenshots. Update the shared fixture, then re-record what changed on purpose.
"What doesn't a screenshot catch?"
Behaviour and accessibility. UI tests tap through the real app, and Apple's accessibility audit checks every screen.
"Flaky tests?"
No automatic retries, because they hide flakiness. Quarantine within 24 hours with an owner, then fix the cause.
"How did you use AI?"
As a pair programmer for research, code and docs. I made the scope and product decisions and approved every result; PROMPTS.md lists the prompts and decisions.
"What would you do differently?"
Start report-only on a real BILD/WELT module earlier, to measure flakiness and run time on real code before making the gate required.
