Demo script

A walkthrough of the project without slides: the repo, the app, how a test works, a green run, a bug caught live, the human decision on GitHub, messy content, safety nets, CI, then Android. About 25 minutes, then questions.

Before you start: one command

Run this in Terminal 15–30 minutes before. It checks your tools, makes sure both branches build and behave (main green, the regression failing on 29), then opens every window you'll point at, in the order you'll need them. About 6–10 minutes.

cd ~/Desktop/Task && presentation/setup.sh
You'll see at the end: "READY" and a list of what is open where. (The regression check prints a failure on purpose: that's the bug the demo catches.)

How to run the demo

  • Files are already open: when the script says "VS Code tab 2", just click that tab. Only the 12 commands you run live have a Copy button: press Copy, Cmd+Tab to Terminal, Cmd+V, Enter, and read the command out loud.
  • Say what to look for before you switch windows or run a command, so people know where to look.
  • Section 6 is the heart of the demo. Never skip it. Short on time: skip sections 8 and 10.
  • If something breaks: don't debug in front of them. Run git checkout main (button at the top), then use the fallback written in that section.
  • Screens: share your whole screen; keep this page on a second device (tablet or phone) or printed.

3. How one screenshot test works

about 3 min

Goal: They understand fixture → render → golden, with real files.

Say

Three pieces. One: the fixture, frozen fake API data. This file is the feed the tests read; this item has premium: true, that's the PLUS article.

Two: the test. One line renders the real production feed screen with that data, in memory, and compares it with an approved picture.

Three: that approved picture, the golden, stored in git. One PNG per screen and variant: light, dark, the largest text size. If the new picture matches, the test passes. If not, it fails and shows me the difference. And here are all 89 approved states on one page.

6. Break it on purpose

about 3.5 min6 live commands

Goal: The core moment: a harmless-looking change is caught.

Say

This branch contains a plausible refactor: "simplify the kicker row, tighten the banner". It's one file, a few lines, and it looks harmless in a code review. By accident it drops the PLUS badge and takes 2 points of padding off the breaking banner.

This is supposed to fail. [While it runs, ~1 min:] Every screen with a PLUS teaser or the banner should go red; everything else should stay green.

29 of 89 screenshots fail, and the other 60 stay green: games, account, the paywall. Here is the diff: the approved picture, the new one, and in magenta the pixels that changed. The badge is simply gone. And the summary already says what kind of change each one is: 10 layout changes, because the banner got shorter, and 19 visible ones. That table is what CI posts on the pull request.

7. A human decides

about 2 min

Goal: Show both outcomes, live on GitHub.

Say

When a pull request fails, a person looks at the diff and decides.

If it's a bug, like this one, we fix the code and the goldens stay. This is that change as a pull request: blocked, with the bot's table.

If the change is intended, like a redesign, we add the record-snapshots label. CI re-records the goldens on its fixed machine, proves them, and pushes them as a bot commit; then a design or QA code owner approves the new pictures. This second pull request did exactly that: rounder cards, 33 screenshots changed on purpose, re-recorded by the bot, then green. Goldens never come from someone's laptop, and approval is never automatic.

8. How much difference is allowed

about 1 min

Goal: Show you thought about tolerance and human confirmation.

Say

Rendering noise no person can see is ignored: a perceptual precision of 0.98 absorbs GPU anti-aliasing. Anything beyond that fails, however small: a 2-point shift and a missing badge are both small, and both are bugs. A pixel count can't tell intent, so the labels are triage, never approval. And tolerance is never loosened globally.

12. Android and rollout

about 2 min

Goal: Show the design transfers to Android, and that you can roll it out.

Say

Everything I showed works on Android the same way. Android reads the same fixture files and uses the same test names, so one regression fails in the same places on both. The tool is Roborazzi on Robolectric: Compose rendered on the JVM, no emulator. I built that version first, and it found real bugs, like a decoder difference that made a PLUS article free on Android. I cut it from the demo to keep today focused; it's in section 10 of the strategy.

To roll it out: start with one app and five design-system components in report-only mode, add the shared fixtures, then make the gate required, in about four sprints. Developers own the tests, QA owns the system around them, and design approves the goldens.

Likely questions

"Who approved these goldens?"
I did, as the code owner. The AI did a first pass and caught real bugs, but approving goldens and merging pull requests were never delegated. That's the process I propose: AI may triage, a human approves.
"A test fails on CI but passes on my Mac. How do I debug it?"
CI is the source of truth and records the goldens. Download the ios-snapshot-diffs artifact from the run; the PR comment already says what kind of change it is. Then check the pinned simulator runtime: the same runtime on the Mac reproduces CI exactly.
"You replaced the native tab bar because the tool couldn't capture it. Would you change product UI for a test tool?"
No, that was a demo shortcut. In production: keep the system tab bar, snapshot the tab content, and cover system chrome in the nightly device layer.
"BILD has years of UIKit and a singleton API client. What do you ship in the first two weeks?"
Snapshots of design-system components that take plain models, a URLProtocol stub serving the fixtures as a stopgap, one client seam at one feature boundary, and CI in report-only mode.
"Show me a regression that passes your tolerance."
A colour change below about ΔE 2, like a slight brand-colour tweak. That's why colour tokens have their own contrast tests, and design reviews token changes.
"How fast and how expensive at scale?"
A full iOS run on GitHub is 12–19 minutes including UI tests. At scale: only affected modules, sharding, iOS only when iOS code changes, the slowest checks nightly. Target: under 10 minutes per PR.
"What about flaky tests?"
No automatic retries, because they hide flakiness. Quarantine within 24 hours with an owner. CI found one real flake, a UI test racing an animation, and I fixed the cause.
"Why only iOS?"
The brief asks for a working demo on at least one platform plus a strategy that covers the other. I built Android first too, then cut it to keep the demo focused; STRATEGY §10 describes it.
"How did you use AI?"
As a pair programmer: research, code, docs, running the tests. I made the scope and product decisions and approved the results; PROMPTS.md lists every prompt and decision.

Can't answer one? "Good question; I haven't measured that. Here's how I'd find out: …", then name the test or experiment.
