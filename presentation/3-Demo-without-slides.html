Demo without slides

Show the project itself, in this order: the repo, the app, how a test works, a green run, a bug caught live, the human decision on GitHub, messy content, safety nets, CI, then Android. About 25 minutes, then questions. Run 1 · Before the presentation first.

How to run it

  • For every section: say the script (or your own words), then press Copy on each command, Cmd+Tab to Terminal, Cmd+V, Enter. Read the command out loud as you run it.
  • Say what to look for before you run a command, so people know where to look.
  • Section 6 is the heart of the demo. Never skip it. Short on time: skip sections 8 and 10.
  • If something breaks: don't debug in front of them. git checkout main, then use the fallback written in that section.

about 1 min

Goal: Say who you are, what they'll see, and that everything is real.

Say

Hi, I'm Saad. Instead of slides, I'll show you the project itself: a small news app in SwiftUI, the screenshot tests around it, and the CI pipeline on GitHub.

The question it answers: how do we catch visual bugs in the BILD and WELT apps, like a PLUS badge that silently disappears, before a reader sees them, even though the news content changes every minute? I'll show how it works, break it on purpose, and show what happens next. At the end, how the same approach works on Android.

3. How one screenshot test works

about 3 min

Goal: They understand fixture → render → golden, with real files.

Say

Three pieces. One: the fixture, frozen fake API data. This file is the feed the tests read; this item has premium: true, that's the PLUS article.

Two: the test. One line renders the real production feed screen with that data, in memory, and compares it with an approved picture.

Three: that approved picture, the golden, stored in git. One PNG per screen and variant: light, dark, the largest text size. If the new picture matches, the test passes. If not, it fails and shows me the difference. And here are all 89 approved states on one page.

Do
  1. VS CodeThe fixture.
    open -a "Visual Studio Code" fixtures/feed/feed_default.json
    You'll see: Point at "premium": true on tsr-002.
  2. VS CodeThe test.
    open -a "Visual Studio Code" ios/NewsKit/Tests/NewsUISnapshotTests/FeedScreenSnapshotTests.swift
    You'll see: func test_feed_default: one line.
  3. FinderThe goldens folder.
    open ios/NewsKit/Tests/NewsUISnapshotTests/__Snapshots__/FeedScreenSnapshotTests
    You'll see: test_feed_default.light.png, .dark.png, .light_xxxl.png…
  4. BrowserEvery golden on one page.
    make gallery && open artifacts/gallery/index.html
    You'll see: 89 screenshots, grouped by test, variants side by side.

6. Break it on purpose

about 3.5 min

Goal: The core moment: a harmless-looking change is caught.

Say

This branch contains a plausible refactor: "simplify the kicker row, tighten the banner". It's one file, a few lines, and it looks harmless in a code review. By accident it drops the PLUS badge and takes 2 points of padding off the breaking banner.

This is supposed to fail. [While it runs, ~1 min:] Every screen with a PLUS teaser or the banner should go red; everything else should stay green.

29 of 89 screenshots fail, and the other 60 stay green: games, account, the paywall. Here is the diff: the approved picture, the new one, and in magenta the pixels that changed. The badge is simply gone. And the summary already says what kind of change each one is: 10 layout changes, because the banner got shorter, and 19 visible ones. That table is what CI posts on the pull request.

Do
  1. TerminalShow how small the change is.
    git diff main demo/regression --stat
    You'll see: 1 file changed.
  2. TerminalSwitch to the branch with the bug.
    git checkout demo/regression
    You'll see: Switched to branch 'demo/regression'.
  3. TerminalRun the tests: they must fail.
    make ios-test
    You'll see: ~1 min, fails: "diff report: 29 failure(s)".
  4. BrowserOpen the diff page.
    open artifacts/ios/diffs/index.html
    You'll see: Scroll to ComponentSnapshotTests/test_teaserCard_premium.dark: golden with PLUS | new without | magenta.
  5. TerminalShow the triage summary.
    cat artifacts/ios/diffs/summary.md
    You'll see: 29 changed (layout: 10, visible: 19, subtle: 0).
  6. TerminalALWAYS switch back to the correct code.
    git checkout main
    You'll see: Switched to branch 'main'.
If it fails: If anything goes wrong: git checkout main, then open docs/regression (the captured CI result). "Here's the captured run."

7. A human decides

about 2 min

Goal: Show both outcomes, live on GitHub.

Say

When a pull request fails, a person looks at the diff and decides.

If it's a bug, like this one, we fix the code and the goldens stay. This is that change as a pull request: blocked, with the bot's table.

If the change is intended, like a redesign, we add the record-snapshots label. CI re-records the goldens on its fixed machine, proves them, and pushes them as a bot commit; then a design or QA code owner approves the new pictures. This second pull request did exactly that: rounder cards, 33 screenshots changed on purpose, re-recorded by the bot, then green. Goldens never come from someone's laptop, and approval is never automatic.

Do
  1. BrowserThe regression pull request.
    open https://github.com/SaadiIftikhar/newsdemo-screenshot-testing/pull/1
    You'll see: Red check; the bot comment: 29 changed.
  2. BrowserThe redesign pull request's commits.
    open https://github.com/SaadiIftikhar/newsdemo-screenshot-testing/pull/2/commits
    You'll see: "snapshot-bot: re-record iOS goldens", then green.
  3. TerminalWho must approve golden changes.
    cat .github/CODEOWNERS
    You'll see: Golden folders need design/QA review.
If it fails: Offline? open docs/regression and show summary.md: "this is what the bot posts".

8. How much difference is allowed

about 1 min

Goal: Show you thought about tolerance and human confirmation.

Say

Rendering noise no person can see is ignored: a perceptual precision of 0.98 absorbs GPU anti-aliasing. Anything beyond that fails, however small: a 2-point shift and a missing badge are both small, and both are bugs. A pixel count can't tell intent, so the labels are triage, never approval. And tolerance is never loosened globally.

Do
  1. VS Code(Optional) The tolerance in code.
    open -a "Visual Studio Code" ios/NewsKit/Tests/NewsUISnapshotTests/SnapshotSupport.swift
    You'll see: perceptualPrecision: 0.98, with the reason in a comment.

10. Safety nets

about 1.5 min

Goal: Show the tests can't pass while protecting nothing.

Say

A blank golden would make a test pass while protecting nothing, so a lint rejects them. Apple's accessibility audit runs on every screen of the real app; it found hidden tabs that VoiceOver could still reach, which no screenshot can show. And my rule: every check is shown to fail once before I trust it.

12. Android and rollout

about 2 min

Goal: Show the design transfers to Android, and that you can roll it out.

Say

Everything I showed works on Android the same way. Android reads the same fixture files and uses the same test names, so one regression fails in the same places on both. The tool is Roborazzi on Robolectric: Compose rendered on the JVM, no emulator. I built that version first, and it found real bugs, like a decoder difference that made a PLUS article free on Android. I cut it from the demo to keep today focused; it's in section 10 of the strategy.

To roll it out: start with one app and five design-system components in report-only mode, add the shared fixtures, then make the gate required, in about four sprints. Developers own the tests, QA owns the system around them, and design approves the goldens.
