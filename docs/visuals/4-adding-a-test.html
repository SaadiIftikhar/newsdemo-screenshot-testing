Adding a new test or state

How to protect a new screen, or a new state of an existing one (an error, an empty list, a new kind of article), from start to merge.

1

Decide what to protect

List the states that matter: loaded, empty, error, offline, long text, the business-critical bits (like the PLUS badge). Each state becomes one test. Light + dark by default; small phone or tablet only where the layout changes.

↓
2

Get the data: reuse or add a fixture

Most states reuse an existing file in fixtures/feed/. For new data, add a JSON file shaped exactly like the real API (images go in fixtures/images/).

The contract tests check every fixture decodes and every image it names exists, so a broken fixture fails immediately.

↓
3

New screen? Build it so a test can create it

Write the view in ios/NewsKit/Sources/ so it takes its data and state as plain inputs. Then the test (and the app) can create it directly in any state, without navigation.

↓
4

Write the test

Add one function per state in the matching file in ios/NewsKit/Tests/NewsUISnapshotTests/: assertScreen for full screens, assertComponent for single components. The function name becomes the golden's file name.

// FeedScreenSnapshotTests.swift: a new state of an existing screen
func test_feed_breakingOnly() throws {
    assertScreen(
        FeedView(state: .loaded(try Snap.store.feed("feed_breaking_only"))),
        variants: [.light, .dark]
    )
}

Illustrative example: this state and fixture don't exist in the project.

↓
5

Record its goldens: make ios-record-missing

Records pictures only for tests that don't have a golden yet. Every existing golden is still compared, so nothing else can change by accident.

↓
6

Look at the new pictures (the step people skip)

Open them in __Snapshots__/<TestClass>/ or run make gallery. A golden is a promise that this is correct; if the screen shows a bug, recording it would lock the bug in. Wrong? Fix the code, delete the PNG, record again.

↓
7

Check: make ios-test and make lint-goldens

Everything green, and no blank goldens.

↓
8

Commit and open a pull request

Commit the test, the new PNGs and any new fixture together, so the reviewer sees the code and the pictures side by side.

↓
9

CI verifies, design/QA approves

CI runs everything (see normal flow). New golden files mean a design or QA code owner must approve them. If CI's machine draws slightly different pixels than your laptop, add the record-snapshots label so CI records the official goldens (see when something changes).

↓
✓

Merge

From now on, every pull request is checked against these new pictures.

Quick reference

I want to…Do this
Add a state of an existing screenSteps 1, 2, 4–9 (no new view needed)
Add a whole new screenAll steps, including 3
Change how an existing screen looks, on purposeChange the code; the existing test fails; follow the intended-change path
Cover a new kind of messy contentAdd it to feed_hostile_content.json; its existing test fails; check and re-record
Remove a stateDelete the test function and its PNGs, so no stale goldens remain
